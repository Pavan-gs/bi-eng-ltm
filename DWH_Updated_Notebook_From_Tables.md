# 1. DIMENSIONAL MODELLING

Dimensional modelling organizes data for analysis.

```text
                 DIM_CUSTOMER
                       |
                       |
DIM_DATE ---- FACT_SALES ---- DIM_PRODUCT
                       |
                       |
                 DIM_LOCATION
```

## Fact

A fact normally represents a business event and contains measurements.

Examples:

```text
FACT_SALES
FACT_ORDERS
FACT_PAYMENTS
FACT_APPOINTMENTS
```

## Dimension

A dimension describes the business entity involved in the event.

Examples:

```text
DIM_CUSTOMER
DIM_PRODUCT
DIM_DATE
DIM_LOCATION
```

Simple rule:

```text
FACT       → What happened?
DIMENSION  → Who / What / Where / When?
```

---

# 2. GRAIN / GRANULARITY

**Grain = what one row represents.**

Before designing a fact table, write:

```text
ONE ROW REPRESENTS ______________________
```

Example:

```text
FACT_SALES
ONE ROW = ONE SALES TRANSACTION
```

Another possible grain:

```text
FACT_SALES_DAILY
ONE ROW = ONE CUSTOMER + ONE PRODUCT + ONE DAY
```

These are different fact-table designs.

## Why grain matters

Suppose order 1001 contains two products:

```text
Order 1001
 ├── Product A → 2 units
 └── Product B → 3 units
```

Order-level grain:

```text
ONE ROW = ONE ORDER
→ 1 row
```

Order-line grain:

```text
ONE ROW = ONE ORDER LINE
→ 2 rows
```

**Do not mix different grains in the same fact table.**

# 5. NATURAL KEY VS SURROGATE KEY

## Natural / business key

Comes from the source system.

```text
CUSTOMER_ID = C101
```

## Surrogate key

Generated by the DWH.

```text
CUSTOMER_KEY = 10001
```

The surrogate key does not need business meaning.

# 6. CREATING SURROGATE KEYS

A simple Snowflake implementation uses an identity column.

```sql
CREATE OR REPLACE TABLE DWH.DIM_CUSTOMER_SK
(
    CUSTOMER_KEY NUMBER AUTOINCREMENT,
    CUSTOMER_ID VARCHAR,
    CUSTOMER_NAME VARCHAR,
    CITY VARCHAR,
    SEGMENT VARCHAR
);
```

Insert source data:

```sql
INSERT INTO DWH.DIM_CUSTOMER_SK
(
    CUSTOMER_ID,
    CUSTOMER_NAME,
    CITY,
    SEGMENT
)
VALUES
('C101', 'Ravi', 'Mumbai', 'Retail'),
('C102', 'Priya', 'Pune', 'Premium'),
('C103', 'Arun', 'Delhi', 'Retail');
```

Check:

```sql
SELECT *
FROM DWH.DIM_CUSTOMER_SK;
```

Conceptually:

```text
CUSTOMER_KEY | CUSTOMER_ID
-------------|------------
1            | C101
2            | C102
3            | C103
```

The exact generated values depend on the identity configuration.

---

# 7. WHY SURROGATE KEYS MATTER

They become especially useful when a dimension has history.

Example:

```text
CUSTOMER_KEY | CUSTOMER_ID | CITY
-------------|-------------|---------
1            | C101        | Mumbai
25           | C101        | Bangalore
```

The business customer is still:

```text
C101
```

but the DWH has two versions.

This is central to SCD Type 2.

# 8. STAR SCHEMA

```text
                 DIM_CUSTOMER
                       |
                       |
DIM_DATE ---- FACT_SALES ---- DIM_PRODUCT
                       |
                       |
                 DIM_LOCATION
```

The fact is in the centre and dimensions surround it.

Example:

```sql
SELECT
    c.CITY,
    SUM(f.SALES_AMOUNT) AS TOTAL_SALES
FROM DWH.FACT_SALES f
JOIN DWH.DIM_CUSTOMER c
    ON f.CUSTOMER_KEY = c.CUSTOMER_KEY
GROUP BY c.CITY;
```

# 11. SLOWLY CHANGING DIMENSIONS

Suppose:

```text
C101 | Ravi | Mumbai
```

changes to:

```text
C101 | Ravi | Bangalore
```

Question:

> Should the old Mumbai value remain?

---

## SCD TYPE 1

Overwrite.

```text
Before:
C101 | Ravi | Mumbai

After:
C101 | Ravi | Bangalore
```

Use when historical values are not required.

---

## SCD TYPE 2

Preserve historical versions.

```text
CUSTOMER_KEY | CUSTOMER_ID | CITY       | CURRENT_FLAG
-------------|-------------|------------|-------------
1            | C101        | Mumbai     | N
25           | C101        | Bangalore  | Y
```

Typical columns:

```text
CUSTOMER_KEY
CUSTOMER_ID
CUSTOMER_NAME
CITY
START_DATE
END_DATE
CURRENT_FLAG
```

Example:

```sql
CREATE OR REPLACE TABLE DWH.DIM_CUSTOMER_SCD2
(
    CUSTOMER_KEY NUMBER AUTOINCREMENT,
    CUSTOMER_ID VARCHAR,
    CUSTOMER_NAME VARCHAR,
    CITY VARCHAR,
    START_DATE DATE,
    END_DATE DATE,
    CURRENT_FLAG VARCHAR
);
```

---

## SCD TYPE 3

Stores limited previous/current information.

```text
CUSTOMER_ID | CURRENT_CITY | PREVIOUS_CITY
------------|--------------|--------------
C101        | Bangalore    | Mumbai
```

Use when limited history is sufficient.

# 13. STAGES

A stage is used as a file location/interface for ingestion.

```text
FILE
 ↓
STAGE
 ↓
COPY INTO
 ↓

```

Internal stage:

```text
Snowflake-managed storage
```

External stage:

```text
External cloud storage
        ↓
      Stage
        ↓

```

Do not confuse:

```text
SCHEMA
→ logical namespace for database objects

STAGE
→ location/interface for data files
```

# 14. FILE FORMAT

A file format tells Snowflake how to read a file.

```sql

SKIP_HEADER = 1
FIELD_OPTIONALLY_ENCLOSED_BY = '"';
```

Mental model:

```text

COPY INTO
```

# 17. DATA PROFILING

Before transforming data, understand the data.

Questions:

```text
How many rows?
How many NULLs?
How many unique values?
Are there duplicates?
Are data types correct?
Are values valid?
```

Row count:

```sql
SELECT COUNT(*) AS TOTAL_ROWS
FROM DWH.RAW_CUSTOMERS;
```

Distinct IDs:

```sql
SELECT COUNT(DISTINCT CUSTOMER_ID) AS UNIQUE_CUSTOMERS
FROM DWH.RAW_CUSTOMERS;
```

NULL check:

```sql
SELECT COUNT(*) AS NULL_CITY_COUNT
FROM DWH.RAW_CUSTOMERS
WHERE CITY IS NULL;
```

Duplicate check:

```sql
SELECT
    CUSTOMER_ID,
    COUNT(*) AS RECORD_COUNT
FROM DWH.RAW_CUSTOMERS
GROUP BY CUSTOMER_ID
HAVING COUNT(*) > 1;
```

# 18. DATA CLEANSING

Example:

```sql
SELECT
    CUSTOMER_ID,
    TRIM(CUSTOMER_NAME) AS CUSTOMER_NAME,
    UPPER(CITY) AS CITY
FROM DWH.RAW_CUSTOMERS;
```

Handling NULL:

```sql
SELECT
    CUSTOMER_ID,
    COALESCE(CITY, 'UNKNOWN') AS CITY
FROM DWH.RAW_CUSTOMERS;
```

The business rule determines the correct treatment of missing values.

# 19. DUPLICATES AND MISSING DATA

Duplicate example:

```text
C101 | Ravi | Mumbai
C101 | Ravi | Mumbai
```

This may occur in RAW/staging input even though the final DWH table has uniqueness rules.

Missing data:

```text
CUSTOMER_ID | CITY
------------|--------
C101        | Mumbai
C102        | NULL
```

Possible actions:

```text
Keep NULL
Replace with UNKNOWN
Derive the value
Reject the record
```

# 23. MERGE / UPSERT — PRACTICAL EXTENSION

Useful for implementing incremental processing.

```text
Incoming record
       |
       ▼
Does key exist?
   /          YES          NO
  |            |
UPDATE       INSERT
```

Example:

```sql
MERGE INTO DWH.DIM_CUSTOMER AS target
USING DWH.STG_CUSTOMER AS source
ON target.CUSTOMER_ID = source.CUSTOMER_ID

WHEN MATCHED THEN
    UPDATE SET
        target.CUSTOMER_NAME = source.CUSTOMER_NAME,
        target.CITY = source.CITY

WHEN NOT MATCHED THEN
    INSERT
    (
        CUSTOMER_ID,
        CUSTOMER_NAME,
        CITY
    )
    VALUES
    (
        source.CUSTOMER_ID,
        source.CUSTOMER_NAME,
        source.CITY
    );
```

Upsert:

```text
UPDATE existing
+
INSERT new
```

# 24. COMPUTE MANAGEMENT

Snowflake separates storage and compute.

```text
STORAGE
   +
COMPUTE
```

A virtual warehouse provides compute.

```sql
CREATE OR REPLACE WAREHOUSE DWH_WH
WITH
    WAREHOUSE_SIZE = 'XSMALL'
    AUTO_SUSPEND = 60
    AUTO_RESUME = TRUE;
```

```sql
USE WAREHOUSE DWH_WH;
```

Important:

```text
Warehouse size
→ compute capacity

Auto-suspend
→ stop unused compute

Auto-resume
→ start when work arrives
```

# 26. MICRO-PARTITIONS

Snowflake automatically organizes table data into micro-partitions.

```text
TABLE
 |
 +-- Micro-partition
 +-- Micro-partition
 +-- Micro-partition
 +-- Micro-partition
```

Useful filters can allow Snowflake to skip irrelevant micro-partitions.

This is **partition pruning**.

# 29. OPTIONAL PRACTICAL EXTENSIONS

These are useful Snowflake/DWH extensions, but they are **not listed as standalone topics in the curriculum extract**.

## CDC

```text
SOURCE
  ↓
Capture INSERT / UPDATE / DELETE
  ↓
Changed records
  ↓
DWH processing
```

CDC answers:

> What changed?

CDC can be implemented by mechanisms at or near the source system. It is not inherently a Snowflake-only feature.

## Idempotency

```text
Process batch A
      ↓
Correct DWH state

Process batch A again
      ↓
Same correct DWH state
```

It is a property of a reliable pipeline.

## Zero-copy cloning

Useful Snowflake feature for isolated testing/development.

```sql
CREATE TABLE DWH.FACT_SALES_TEST
CLONE DWH.FACT_SALES;
```

## Time Travel

Useful Snowflake capability for accessing/recovering supported historical table states within the applicable retention period.

These should be treated as **extensions**, not as replacements for the core syllabus.
